从 OOM 到稳定运行：一次 Java 大数据定时任务的内存与性能优化实践

适用场景：Spring 定时任务、Java 8、MyBatis、PostgreSQL；单次处理数百万用户记录，并进行分组内两两比较，最后批量入库。
核心目标：在不改变业务口径的前提下，控制峰值内存、减少数据库往返、降低对象与字符串分配，并让任务失败可见。

一、问题背景：为什么任务会 OOM？

任务 ImportUserFiberIssueJob 的目标是计算同一 PON 口下用户之间的光衰差异，识别光纤风险账号，最终写入 ctcq.user_fiber_issue。

主要流程：

  1. 查询 PON 口下的活跃账号；
  2. 按 LOID 查询光衰，并回填到用户记录；
  3. 按 telnetip + telnetport 分组；
  4. 在同一 PON 口内进行两两比较；
  5. 为风险账号生成 fiberDetail；
  6. 批量插入结果表。

这个任务的压力不只来自“查询了多少行”，更来自计算过程中额外创建了多少对象，以及这些对象能存活多久。

假设查询得到数百万行数据。每一行可能是一个 Map，Map 内部又有哈希表节点、键和值等对象。除此之外，任务还会构造：

  • 去重 LOID 集合和列表；
  • LOID → 光衰的映射；
  • PON 分组 Map、分组 List；
  • 风险等级 Map；
  • 明细 StringBuilder；
  • 最终待插入实体 Map；
  • 并发执行时的分片 List、任务对象。

如果所有阶段的中间结果都长期保留，峰值内存可能远高于数据库返回字段本身的体积。

多个查询任务可能同时写入 lightMap。普通 HashMap 不适合被多个线程无同步地并发修改。ConcurrentHashMap 支持并发访问。

4.4 并发不等于无限加线程

线程数应受数据库连接池约束。比如连接池最大连接数为 10，查询并发设置为 5，还需要给其他业务请求、任务和事务留出连接余量。

并发查询的收益来自 I/O 等待期间让其他任务继续执行，不代表 SQL 本身一定更快。若数据库已经是瓶颈，提高并发可能造成：

  • 连接池排队；
  • 数据库 CPU/IO 压力增加；
  • 锁竞争和缓存争用；
  • 单条 SQL 延迟上升。

因此需要观察连接池活跃数、等待数、SQL 耗时和数据库资源，而不是只看线程数。

6.1 为什么不能随意按用户行切片？

假设一个 PON 口有 100 个账号。如果按行拆成两个 50 行分片，那么第一片和第二片之间的用户不会互相比较，风险结果就不完整。

6.3 clear() 和 null 分别有什么作用？

这是这次内存治理中的关键知识点。

  • rows.clear()：清空当前分组 List 持有的元素引用；
  • ponGroups.set(g, null)：让外层分组列表不再引用这个分组 List；
  • entityList.clear()：插入完成后，释放实体列表持有的 Map 引用。

但要准确理解：clear() 不是手动释放堆内存，也不保证 JVM 立刻归还内存。 它只是断开对象引用。当对象不再被任何 GC Root 可达时，才有资格被垃圾回收。堆内存何时回收由 GC 决定。

此外，clear() 不会把一个对象的容量自动缩到最小；它主要清除元素引用。当前代码将大对象的引用链及时断开，减少对象长期存活的机会。

七、优化五：只让风险账号进入明细和待插入实体阶段

无风险账号仍然参与比较，但不落库。

这样可以减少：

  • 最终实体 Map 的数量；
  • 批量 INSERT 的行数；
  • 明细长期存活的对象数量；
  • 数据库写入与 WAL 产生量（实际收益需结合数据库观测）。

不过，风险账号的 fiberDetail 仍可能很大，尤其是异常大口中，单个账号可能与大量账号产生风险比对。因此后续仍需监控最大口径和最大明细长度。

八、优化六：两两比较的算法与数据结构

8.1 时间复杂度

一个 PON 口有 n 个用户时，全部两两比较次数为：

[
\frac{n(n-1)}{2}
]

即时间复杂度为：

[
O(n^2)
]

示例：

用户数 两两比较次数
100 4,950
1,000 499,500
5,000 12,497,500
10,000 49,995,000

这意味着大口的计算量会迅速增长。分片能够控制内存生命周期，却不能消除单个超大 PON 口的二次复杂度。

浮点边界必须谨慎

当前代码中的 FAST_SKIP_THRESHOLD = 10.0D，其注释强调业务数据精度和 double 误差评估。

需要指出一个通用原则：浮点误差不能仅凭“通常很小”就认定不会漏判。 如果数据来源、精度或计算过程变化，快速跳过条件可能需要重新验证。

例如，如果业务允许任意精度小数，那么理论上可能存在一个真实差值略大于 10、但 double 运算结果不大于 10 的边界情况。

更稳妥的工程做法：

  1. 明确数据库字段类型、输入精度和取值范围；
  2. 用边界样本验证 10、10.0001、15、15.0001 等值；
  3. 对比优化算法与纯 BigDecimal 参考算法的结果；
  4. 若要求严格数值正确性，可采用整数定标、保守误差界，或直接精确计算。

不能为了性能牺牲业务正确性。

可变的 StringBuilder 更适合这种循环累加场景。

十三、为什么这些措施能缓解 OOM？

这次改造的重点是减少不必要的对象存活时间和重复数据结构。

改造前的典型风险

随着处理推进，多个阶段的数据可能同时留在堆中。

改造后的主要思路

主要收益：

  1. 数据库往返减少：避免逐 PON 口重复查询；
  2. 光衰查询去重：相同 LOID 不重复查；
  3. 并发受控：限制同时运行的分片数；
  4. 明细按需生成：正常比对不产生明细；
  5. 风险账号才转实体：减少实体和写入量；
  6. 按完整 PON 口分片：保证计算正确性；
  7. 插入后及时断开引用：避免所有明细跨批累积；
  8. 数组预解析：降低内层循环重复解析成本。

这些措施并不意味着对象会立刻从堆中消失，而是让不可达对象更早出现，使 GC 有机会回收。

  4. 必要时在安全环境生成 heap dump；

十五、这份实现仍需关注的风险与后续优化

优化成功处理 OOM 是一个重要结果，但仍不代表所有规模下都安全。

15.1 全量原始行仍然常驻

recordList 在光衰回填和分组期间持有全部原始记录。分组后，recordList.clear() 可以清除它自己的元素引用，但分组 List 仍然持有每一行。

如果基础数据继续增长，原始行本身仍可能成为内存瓶颈。

可考虑：

  • SQL 只返回实际需要的字段；
  • 使用轻量 POJO/数组替代通用 Map；
  • 在满足完整 PON 口约束的前提下，按设备范围流式处理；
  • 对超大 PON 口做独立策略；
  • 通过临时表先物化必要数据，再分段计算。

15.2 单个超大 PON 口仍可能 OOM 或耗时过长

分片单位是 PON 口。如果某个口本身拥有数千甚至上万账号：

  • 比较次数为 O(n²)；
  • 风险明细可能很大；
  • 单口的 StringBuilder 和实体数量可能非常可观。

可以考虑按光衰排序后的算法优化风险识别。但如果还需要输出所有满足 diff > 10 的账号对，输出规模本身可能达到二次量级，无法仅靠算法消除。

必须先明确业务究竟需要：

  • 每个账号的最高风险；
  • 每个账号任意一条风险证据；
  • 还是所有风险比对明细。

不同输出要求对应不同算法与存储设计。

15.3 fiberDetail 的数据库字段容量

需要核对目标字段类型和长度。单个账号的明细可能随着口规模增大而快速变长。

应统计：

  • 最大长度；
  • P95/P99 长度；
  • 单口风险比对数；
  • 插入失败是否存在字段长度或协议限制。

15.4 分片插入的原子性与任务重跑

当前是分片写入。若前 20 片成功，第 21 片失败，目标表可能已经有部分结果。

这会带来：

  • 手动重跑重复插入；
  • 同一账期结果不完整；
  • 升级任务处理到部分数据。

建议设计清晰的幂等策略，例如：

  • 以账期 + 业务唯一键建立唯一约束；
  • 使用 staging 表，完整计算后再切换；
  • 先删除指定账期再重算（需评估并发与事务影响）；
  • 用任务状态表记录开始、成功、失败与阶段；
  • 将写入设计成可安全重试。

不要在未确认业务唯一键前，直接对现有表增加唯一约束。

15.5 AtomicBoolean 是 JVM 内锁，不是分布式锁

多实例部署时，每个实例都有自己的 AtomicBoolean。若定时任务可能在多个节点同时执行，需要分布式调度或数据库级互斥。

十七、总结

这次 OOM 优化的核心，并不是某个“神奇参数”，而是重新设计了数据在任务中的流动方式：

  1. 数据库侧减少重复查询；
  2. 查询侧按 LOID 去重、分批和受控并发；
  3. 计算侧按完整 PON 口分片；
  4. 算法侧减少 Map 查找、精确数值运算和字符串创建；
  5. 存储侧只落有风险账号，并批量插入；
  6. 生命周期侧及时清空容器、断开引用；
  7. 任务侧限制并发、记录异常、避免重复执行；
  8. 验证侧用阶段耗时、堆趋势和 GC/堆分析形成闭环。

最值得记住的一句话：

大数据任务的内存优化，关键不只是减少数据量，而是减少重复数据结构、控制并发在途量，并缩短大对象的存活时间。

同时，OOM 被解决只是阶段性成果。随着用户规模、单口规模和风险明细长度继续增长，还需要持续验证算法复杂度、数据一致性、重跑幂等性和数据库承载能力。
